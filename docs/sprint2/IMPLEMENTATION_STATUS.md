# Sprint 2 — Core sale and payment recovery

**Source baseline:** backend and frontend `origin/main` merged Sprint 1. Sprint 2 source branch `feat/s2-core-sale-payment-20260926` in isolated worktrees. The agreed sprint plan labels this S2 (19–30 October 2026), but this is an early development checkpoint, not a release-date promise.

**Release invariant:** A single purchase may produce at most one paid sale and one stock decrement. A provider payment whose finality is unknown remains recoverable without creating a second charge. Quoting alone neither sells nor reserves stock.

## Slice 1 — Immutable server-authoritative quote

- `POST /api/v2/sales/quotes` requires authenticated owner/admin/cashier, `core_pos`, authorized selected outlet and matching `outletId` body. Input: product/variant/price-level/quantity, optional customer and bounded `discountPercent`. Monetary subtotals or totals supplied by a client are ignored; discount codes are rejected until a server-side promotion policy exists.
- Resolve the active variant, price level and quantity rules using `IRetailSaleResolver`; validate combined duplicate-line stock. Server computes line/subtotal/discount/configured tax/total with two-decimal rounding. Persist immutable tenant/outlet-scoped JSON snapshot and quote version; expire after five minutes. Return a correlation ID. `GET /api/v2/sales/quotes/{quoteId}` returns snapshot + effective expired state; foreign tenant/outlet returns 404/403. Quote has `stockReserved=false`; no transaction/payment/stock history is written.
- `sale_quotes` migration `20260926110327_AddSprint2SaleQuoteSnapshots` is additive; the historical hosted-checkout migration is present in source and EF history. Data and rollback: use only isolated DB for this candidate; a production rollout requires a fresh backup and a new rehearsal. A schema rollback drops quote records; never auto-run it on production.
- Typed FE transport adapter exists in `src/lib/saleQuote.ts`; default cash/QRIS checkout remains on existing endpoints. A separate explicit Sprint 2 QA-only flag can opt retail cash into quote-backed commit; no production merchant is switched until real PG concurrency/payment recovery gates pass.

## Slice 2 — Quote-backed idempotent cash commit (source + isolated QA migration)

- `POST /api/v2/sales/cash` requires a matching quote ID/version, an explicit `Idempotency-Key` (16–128 permitted ASCII chars), selected authorized outlet and amount received. It returns the existing transaction DTO plus `replayed` and correlation ID. Same key+same request returns the same paid sale; same key+changed payload returns 409; a consumed quote cannot be reused with another key. No extra provider payment is created.
- Reprices the selected catalog and tax after a shared PostgreSQL transaction-scoped tenant lock, rejects stale quotes/expired versions/insufficient stock, and uses the existing cash TransactionService under the outer transaction for customer points, sale snapshots and stock history. Legacy cash writer participates in this lock. This lock is not yet used by the QRIS finalizer, so the **full cross-method stock race remains an open release gate**.
- Additive migration `20260926113833_AddSprint2QuoteCashCommit` stores consumed transaction, request hash, key and a unique tenant/outlet/key index; the quote retains original manual-vs-automatic tier selection and item notes. Typed FE `commitCashSale` requires the caller to reuse a stable idempotency key; default checkout is unchanged, with a separate QA-only opt-in implemented in Slice 4.
- Source Release build and full tests **185/185 PASS**. Unit/API regressions cover same-key replay without duplicate sale/stock history, changed-key conflict and stale-stock rejection. Migration on dedicated clone `neverfade_s2_cash_gate` PASS: **23 EF migrations**, all three new columns present. S2 API service runs on loopback port 5133 against that QA-only DB, payment mode disabled. Earlier quote DB and service configuration are preserved for rollback.

## Slice 3 — Verified webhook ordering and uncertain provider-create recovery (source)

- QRIS create now separates local preflight failure from an **ambiguous external create response**: after provider dispatch, a timeout/invalid reply cannot mark the original sale failed or authorize a duplicate payment. API returns `503 PAYMENT_CREATION_UNCERTAIN`; the original `creating` attempt remains discoverable via `/api/payments/current` and blocks another QRIS request for that outlet. This is deliberately conservative, not a successful payment or indefinite automatic resolution claim.
- An authenticated provider webhook can recover an original accepted attempt using its globally unique immutable NeverFade `reference_id` when the initial payment route is absent. Verify original tenant record, amount, currency, channel, request ID, and callback token; register route under the same tenant PostgreSQL advisory lock before sale finalization. A wrong amount is rejected and cannot insert a route or finalize stock. If a webhook arrives before create response, response registration reloads terminal state under lock instead of downgrading paid to pending.
- Provider-confirmed expiry and cancellation re-read status under the same lock before changing state. Paid is monotonic; late failure after capture cannot downgrade transaction/ledger, and a late verified capture after earlier failure is ledger/stock idempotent. External provider network calls remain outside held stock locks.
- UI recognizes `creating` without provider request ID, displays the immutable reference and an explicit uncertain state, offers status check, and hides unusable QR/cancel actions rather than inviting another charge. Admin/provider reference lookup, formal exception-queue resolution and safe continuation of other sales still require product design/verification.
- Source gates: **190/190 backend Release tests PASS** (including accepted-create-then-lost-reply, forged amount denial, callback-before-create-response, duplicate/out-of-order webhook, provider-confirmed expiry); **20/20 QRIS browser mock regressions PASS**, FE build/lint PASS. The UI now immediately restores the original server attempt on a `503 PAYMENT_CREATION_UNCERTAIN` response rather than leaving a retryable checkout button. Existing isolated QA service remains payment-disabled; these provider tests are mocked API integration tests, **not Xendit production calls**.
- A proposed real-PostgreSQL concurrent cash write smoke was blocked by the remote execution safety gate. No success is inferred, and no alternative execution path was used to bypass that gate. Required S2 concurrency and provider financial/UAT gates remain OPEN.

## Slice 4 — QA-only opt-in retail cash checkout (frontend source)

- The existing cash/QRIS checkout remains unchanged unless **`VITE_S2_CASH_CHECKOUT=enabled` is deliberately set at Vite build/dev startup**. Only `general_retail` and `fashion_retail` cash sales use this path; table/restaurant, laundry and all QRIS flows stay on existing endpoints. No existing deployed frontend has this flag enabled.
- Checkout creates server quote with selected authorized outlet, customer, product/variant, requested price level, quantities, notes and discount. Cash commit occurs only when quote status/identity, server discount, server tax rate and two-decimal grand total agree with what the cashier sees; monetary client payload cannot override it. `showTax=false` means zero displayed tax even when a historical `defaultTax` is nonzero. Manual tax input is disabled with a server-policy hint in opt-in cash mode.
- Before the write, the browser persists original quote ID/version, received amount, outlet and stable 32-char idempotency key in **tenant-partitioned sessionStorage**. An ambiguous response, receipt-read failure or reload preserves that record and locks **all** new checkout methods until `Pulihkan Transaksi Tunai` safely replays the *exact* original request/key. The server's returned transaction ID then drives receipt/history lookup. Only a verified successful commit/replay or explicit server no-sale rejection after the commit lock can release the record; timeout/network/5xx cannot. This is not a claim that session storage is a substitute for server-side pending-attempt discovery.
- Frontend QA flag smoke **12/12 PASS across desktop/tablet/mobile** (one quote + commit, timeout/reload same key, no money-amount mismatch payment, verified expired quote unlock). The default flag-off QRIS+legacy cash regression **21/21 PASS**. Frontend production build and lint PASS; large bundle warning advisory.
